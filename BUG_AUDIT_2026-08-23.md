A full-project correctness pass across every module, requested before starting any new
Phase-6+ work: "find all the bugs... go through everything we've already done... find
possible ways to make the already existing structure better."

**Headline finding: all 256 unit tests pass, and this audit still found 1 critical and
3 high-severity bugs.** A green test suite means the code does what its tests say it does
— it does not mean the tests asked the right questions. Every finding below slipped through
256 passing tests; several are annotated with exactly why the existing test missed them.

## Bugs found, by severity

### CRITICAL

#### 1. Every warm-started personal fusion model is trained with the prior applied in the wrong coordinate space
**File**: [code/retrain_from_sessions.py:263-264, 311-312](code/retrain_from_sessions.py)

`load_population_prior()` loads `prior['scaler']` — the `StandardScaler` the population
prior's weights (`w_prior`/`b_prior`) were actually fit in. But both `evaluate_lambda()`
(used for the printed lambda comparison) and `process_mode()`'s final save-worthy fit
**discard that scaler and fit a brand-new one on the user's own small session sample**:

```python
# process_mode(), the fit that actually gets saved to disk
sc = StandardScaler().fit(X)                                    # personal scaler
w, b = fit_logreg_with_prior(sc.transform(X), y, w_prior, b_prior, best_lam)  # w_prior is in POPULATION scaler units
```

The regularizer `(λ/2)‖w − w_prior‖²` only means anything if `w` and `w_prior` live in the
same standardized units. They don't — `w_prior` was fit in the population's per-signal
mean/std; `w` is fit in this user's own. `prototype_warmstart_personalization.py` (the
research script this was ported from) gets this right — it reuses one shared scaler
throughout. The port to `retrain_from_sessions.py` dropped that precondition, and its
docstring warning along with it.

**Consequence**: `process_mode()` unconditionally sets `best_lam = lam` (the warm-started
value) whenever a prior exists (line 307) — there is no accuracy comparison gating this.
Since `models/meta_learner.joblib` already exists on disk, **this is the only kind of model
this script will ever save** once any task mode reaches the 6-session activation threshold.

**Reproduced against the real, unmodified code** (synthetic 6-session fixture with a
realistic personal-calibration offset from the population, written only to a scratch temp
dir): `lambda=0` (from-scratch) scored 100% frame accuracy; the warm-started model that
actually got saved scored **79.2%**. A more adversarial but still plausible scale mismatch
drove it to 37% (worse than chance) against ~99% for both alternatives.

**Why the tests missed it**: `test_process_mode_with_prior_is_warm_started` only asserts on
`blob['warm_started']`/`blob['lambda']` metadata, never on the fitted model's accuracy — and
its synthetic prior data (mean 0, std 1) happens to have a large scale mismatch against the
synthetic personal data ([0,1] range) but nothing asserts that this should matter.

**Fix direction** (not applied — audit is read-only): in both `evaluate_lambda()` and
`process_mode()`'s final fit, transform `X` with `prior['scaler']` instead of fitting a
fresh one, whenever `prior is not None`; only fit a fresh scaler in the true no-prior path.

**Not currently live-triggerable**: every task mode is still below the 6-session bar (per
PLAN_FOR_PP2.md's status snapshot), so no corrupted model has actually been produced or
activated yet — this is a bug in code that would run correctly-looking-but-wrong the moment
personalization first activates, not a bug that has already shipped bad output.

### HIGH

#### 2. A mid-session camera failure can silently duplicate a session in the database
**File**: [code/app.py:1509-1524](code/app.py) (failure branch), interacting with
`save_current_session()` at [code/app.py:816-838](code/app.py)

When `cap.read()` fails mid-capture (webcam unplugged/glitches), the handler sets
`running = False` and calls `save_current_session()` — but never clears
`st.session_state.history` and never calls `st.rerun()` (independently confirmed: no
`st.rerun()` appears between lines 1463 and 1697 of `app.py`). The sidebar, already rendered
earlier in the same script run, still shows a live **Stop** button. Clicking it (the user's
only apparent next action) re-runs `save_current_session()` on the still-populated
`history`, and `session_history.save_session()` always does a plain `INSERT` with no
dedup guard — producing a second, fully-duplicated DB row (same samples), overwriting the
first row's `pending_self_report` reference so the *first* row is left permanently
unlabeled, and misattributing the real intervention log to the *second* (duplicate) session.

**Fix direction**: clear `st.session_state.history` and call `st.rerun()` in the failure
branch, matching every other path that ends a session.

#### 3. The blink-rate estimator overestimates by 2–6x during the first ~15–30s of every session
**File**: [code/behavioral_features.py:268-276](code/behavioral_features.py)

```python
window_elapsed = max(1.0, min(BLINK_WINDOW_SECONDS,
    now - (state.blink_times[0] if state.blink_times else now - 1)))
blinks_per_minute = len(state.blink_times) * (60.0 / window_elapsed)
```

This extrapolates a full-minute rate from however much of the 60s window has *actually*
elapsed since the oldest buffered blink — which is always small right after
`finish_calibration()` clears `blink_times` (i.e., at the start of literally every
calibrated session). **Numerically verified** by replaying the exact deque logic: one blink
at t=0 → reported rate `60`/min; a normal double-blink 0.9s apart → `120`/min; a steady
20/min blinker only converges to the true rate after the full 60s window fills. With
`DEFAULT_BLINK_RATE_BASELINE=12.0`/`BLINK_EXCESS_SCALE=15.0`, these transient readings clip
`blink_stress` straight to `1.0` — a spurious full-scale stress spike from ordinary blinking
at the start of every single session, feeding directly into the fused stress index.
Existing tests run fast enough (milliseconds for ~40 iterations) that they hit this exact
inflation but only assert loose bounds (`>0.0`, `<5.0`) that don't catch it.

**Fix direction**: don't extrapolate to a full minute from a short window — either wait
until the window has enough history (e.g. return `None`/skip the signal for the first ~15s,
consistent with the project's existing "say so rather than guess" abstention pattern used
elsewhere), or use a rate estimator with an explicit warm-up floor on `window_elapsed`.

#### 4. `run_all_evaluations.py`'s mode filter silently pools *any* unparseable modern filename into "Default," not just legacy names
**File**: [code/run_all_evaluations.py:95-99](code/run_all_evaluations.py)

```python
def matches_mode(path):
    if mode is None: return True
    meta = parse_filename(path.name)
    return meta['mode'] == mode if meta else mode == 'default'
```

The docstring justifies this as handling only the old 2-part `relaxed_1.csv` legacy naming.
The code is broader: `parse_filename()` returns `None` for *any* name it can't invert —
including a modern, well-formed-looking name with one corrupted field (e.g. an embedded
underscore in a hand-edited subject ID, which `test_export_naming.py` already proves breaks
parsing). `RECORDING_PROTOCOL.md` explicitly anticipates hand-renaming files. A
Hospital-mode recording renamed with a stray underscore would silently count toward the
**Default**-mode section's numbers while silently vanishing from the **Hospital**-mode
section — the same "which files were really in this number" corruption class the project's
own `RECORDING_PROTOCOL.md` was written to prevent (the `relaaxed_2.csv` incident). No test
file exists for `run_all_evaluations.py` at all, so nothing currently catches this.

**Fix direction**: after `collect()` runs for all modes, cross-check that every
`relaxed_*.csv`/`stressed_*.csv` in the folder was claimed by exactly one mode section, and
print a loud warning listing any file that wasn't (this also directly re-catches a repeat of
the project's founding bug, see Appendix A).

### MEDIUM

#### 5. Per-user detection state (blink/EAR/PERCLOS history) is never reset across a user switch
**File**: [code/behavioral_features.py:94-106, 133](code/behavioral_features.py),
[code/app.py:844-862](code/app.py) (`apply_user_profile`)

Switching the active user swaps `engine.baseline` (the calibrated thresholds) but never
touches `engine.state` — the raw 60s blink/PERCLOS window and 30-frame EAR/head-tilt
history, held in one process-wide singleton (`get_feature_engine()` is `@st.cache_resource`).
If User B is selected within ~60s of User A's session (the exact team-recordings workflow
Phase 1 is building toward), B's first blink-rate/PERCLOS readings are computed from a mix
of A's and B's raw samples, scored against B's baseline. `reset_baseline()` has the identical
gap — it clears `self.baseline` but not `self.state`, so "Reset baseline" doesn't fully
reset detection state despite its name.

**Fix direction**: give `BehavioralFeatureEngine` an explicit `reset_state()` (clearing
`blink_times`/`ear_history`/`head_tilt_history`/`perclos_samples`) and call it from
`apply_user_profile()` and alongside `reset_baseline()`.

#### 6. "Calibrate" doesn't clear `st.session_state.history`, unlike every sibling button
**File**: [code/app.py:1090-1099](code/app.py)

Start, Clear view, and Delete all history all reset `history = []` alongside
`viewing_session_id`/`label`/`task_mode`/`self_report`. Calibrate resets the latter four but
forgets `history`. Concrete scenario: View saved session A → click Calibrate → after
calibration, `viewing_session_id` is `None` but `history` still holds A's samples — the
summary panel renders A's timeline as if it were a fresh current session, and "Download PDF
report" labels it with the *current* task mode and `self_report=None` instead of A's real
values. Same "sibling state forgotten" pattern already fixed once this session for the
`viewing_session_task_mode`/`self_report` pair — recurring here for `history` itself.

#### 7. "Reset baseline" doesn't persist for a named active user
**File**: [code/app.py:1133-1140](code/app.py)

The button's own tooltip says it "wipes the personal baseline back to generic defaults," but
it only calls `engine.reset_baseline()`/`reset_daisee_baseline()` (in-memory only) — never
`session_history.save_user_baseline()`. For a named profile, switching away and back reloads
the pre-reset baseline from the DB, silently undoing the reset.

#### 8. A self-report answered right after Stop isn't reflected in that same session's PDF export
**File**: [code/app.py:1679-1744](code/app.py)

The PDF-export block only reads `self_report` from `viewing_session_self_report` (populated
by the "View" flow on a saved session) — never from a self-report just answered on the
live-just-recorded session. Stop → answer "4" in the banner → immediately download the PDF →
it says "Self-reported stress: not answered," even though the DB row is correct. Only
self-heals if the user re-opens the session later via "View."

#### 9. `session_scores`-style "session" means something different in `train_meta_learner.py` than in `eval_scoring.py`
**File**: [code/train_meta_learner.py:143-155](code/train_meta_learner.py) vs.
[code/eval_scoring.py:95-120](code/eval_scoring.py)

`train_meta_learner.summarize()` defines a "session" as (subject, binary condition) — so a
subject's T2 and T3 UBFC-Phys clips (two different stressors, two different recordings) get
pooled into one majority vote. `eval_scoring.session_scores()` (used by the harness's other
sections and by `ablation_study.py`) defines a session as one recording/file. Both numbers
appear side-by-side in the same regenerated `CANONICAL_RESULTS_*.txt` under the same word,
"session," meaning two different things. Intentional per a code comment, but a real
metric-definition drift between two sections of the one file that's supposed to be the
single source of truth.

#### 10. `ablation_study.py`'s fusion-weight math is a hand-reimplementation with no automated equivalence test
**File**: [code/ablation_study.py:115-136](code/ablation_study.py)

Only `TemporalSmoother`/`HysteresisLevel` are literally imported from `stress_fusion.py`;
the weight-normalization + rule-boost formula in `fused_frame()` is re-derived by hand and
was verified bit-exact **once, manually** (per PLAN_FOR_PP2.md, 2026-08-22) — not by a
regression test that calls the real `compute_stress_index()`. Currently correct; would
silently drift out of sync the moment `compute_stress_index()` changes (e.g. `W_RPPG` being
raised above 0.0, which the project's own README says is the plan).

#### 11. `LiveRPPG`/`BehavioralFeatureEngine` don't defend themselves against a face-loss gap
**File**: [code/rppg_live.py:162-172, 235-250](code/rppg_live.py),
[code/behavioral_features.py:236-241](code/behavioral_features.py)

Both classes early-return from their own internal eviction/update logic when no face is
detected, rather than in `status()`/`estimate()` noticing staleness. Reproduced at the class
level (5 minutes of simulated no-face `add_frame()` calls → `status()` still confidently
reports the frozen 15s-old heart rate). **Currently masked**: both real call sites
(`app.py`, `evaluate_video_file.py`) independently guard with `if face_crop is None:
continue` before ever reaching these methods — so it's not reachable today, but it's a
property the classes should guarantee themselves rather than relying on every future caller
to reimplement the same guard correctly (their own docstrings promise exactly this
"say so rather than guess" behavior).

#### 12. Intervention outcome tracking can silently drop a measurement if the cooldown/eval-window invariant is ever violated
**File**: [code/intervention_agent.py:136-151](code/intervention_agent.py)

The `elif` branch that lets a still-unresolved intervention "expire" its show window falls
through to the targeting/firing logic without protecting `self._active`. Nothing currently
prevents a *second* intervention from starting before the first resolves except that
`INTERVENTION_COOLDOWN_SECONDS (180) > INTERVENTION_EVAL_SECONDS (150)` — an invariant
that's not asserted or documented as required. Reproduced by lowering the cooldown alone:
the first intervention's helped/no-effect outcome is lost with no error, silently corrupting
the effectiveness log the whole feature exists to build.

## Structural / "make the existing thing better" observations (not bugs)

These don't produce wrong output today; they're places where the codebase's own stated
principles (shared logic instead of duplication, "one script regenerates every number,"
provably-identical live/offline paths) aren't fully carried through yet.

- **`eval_scoring.py` and `run_all_evaluations.py` — the modules computing every accuracy %
  and confidence interval this project reports — have no dedicated test file.** Every other
  module in the evaluation harness has one. Finding #4 above is a direct consequence. This
  is the single highest-leverage test-coverage gap in the project given how
  scientific-integrity-critical this code is.
- **No cross-check that every `.csv` in `evaluation_data/` is claimed by exactly one
  harness glob.** This is the project's own founding bug pattern (`relaaxed_2.csv`, 48
  samples silently excluded for months). A one-time pass at report-generation time — list
  any file not matched by any known pattern — would catch a repeat automatically instead of
  requiring a manual audit to find it.
- **`session_history.load_recent_sessions()` has no `user_id` filter.** Every user
  currently sees and can load every other user's session history in the sidebar. This may
  be an intentional "one shared history log" design, but nothing documents it either way,
  and it's worth a deliberate decision now — before team recordings (the very next planned
  milestone) makes it a live, multi-person concern rather than a single-user hypothetical.
- **`stress_detector.py`** (the headless OpenCV-only runner) has its own local
  `ensemble_predict()`/`prep()` and a hardcoded crop-padding constant instead of importing
  `daisee_ensemble.py`/`config.FACE_CROP_PADDING` the way `app.py` and
  `evaluate_video_file.py` now both do. Values currently match, but this is exactly the kind
  of drift-prone duplication the project has spent this session eliminating everywhere else.
  It also has one small dead constant (`DAISEE_CLASS_NAMES`, never referenced).
- **`app.py` calls `engine.face_mesh.process(rgb)` twice per frame** — once directly (for
  `crop_face()`) and again inside `engine.extract()`. Deterministic, so not a correctness
  bug, but doubles FaceMesh inference cost on every processed frame.
- **The "skip a frame with no face" guard that currently protects finding #11 is duplicated
  independently** in `app.py` and `evaluate_video_file.py` rather than being a property
  `LiveRPPG`/`BehavioralFeatureEngine` enforce themselves. Two independent copies of a safety
  guard is one more place for a future edit to forget it.
- **`process_mode()`'s `best_lam`/`best_acc` naming implies a selection between candidates
  that doesn't actually happen** — it's unconditionally the warm-started value whenever a
  prior exists. Renaming or restructuring this would have made finding #1 far easier to spot
  on read-through, and is worth doing regardless of the fix for #1.
- **Offline training/preprocessing scripts have no test files at all**:
  `daisee_preprocessing.py`, `rebucket_to_binary.py`, `train_daisee_stress.py`,
  `wesad_calibration.py`, `lstm_preprocessing.py`, `train_lstm.py`. Reasonable given they're
  GPU/manual-run scripts, but `wesad_calibration.py`'s unit-mislabeling bug (#17) shows even
  a currently-inert script benefits from basic sanity tests.
- **`evaluate_threshold_sweep.py` writes `models/optimal_thresholds.json`, but nothing reads
  it back** — grep-confirmed write-only. Currently vestigial relative to the rest of the
  pipeline.
- **`run_all_evaluations.py` re-globs and re-parses the same `evaluation_data/` folder five
  times per run** (once per mode section) — pure inefficiency, not correctness, not worth
  fixing until the dataset is much larger.
- **`app.py` has no test file of its own** beyond the one pure `session_analytics_dataframe()`
  function (already documented/acknowledged). Findings #2, #6, #7, #8, #13, #14 above are all
  pure `st.session_state` transitions with no camera dependency — they'd be realistic
  candidates for a lightweight button-handler/state-machine test harness if one is ever built,
  without needing a real camera at all.

## What this audit did **not** cover

- The actual camera-driven capture loop (`cv2.VideoCapture`, MediaPipe on live frames) —
  untestable without touching a real webcam, which remains off-limits per standing project
  policy.
- Real training runs (`train_daisee_stress.py`, `train_temporal_model.py` via
  `.venv-train`, `wesad_calibration.py` against the real WESAD dataset) — these take
  hours/need GPU and would have modified `models/`/`data/` artifacts; reviewed by code
  tracing and targeted scratch-script verification instead.
- Running `run_all_evaluations.py`/`train_meta_learner.py --save`/`daisee_test_eval.py` for
  real, which would overwrite production artifacts under `models/`/`evaluation_data/` — the
  harness's logic was verified by tracing and by its existing tests instead.
- The multi-user "Add user" flow's live UI interaction (blocked by a browser-automation
  limitation this session, not by anything in the app — see Methodology above); its
  underlying logic is covered by 6 passing unit tests instead.
- Concurrent/multi-process usage in general (single-user, single-process Streamlit app by
  design) beyond the one TOCTOU note above.
