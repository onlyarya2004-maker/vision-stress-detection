## Findings

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | **High** | `wesad_calibration.py`'s `extract_resp_rate()` used `scipy.signal.butter()`'s default transfer-function `(b, a)` form for a 0.1–0.5 Hz bandpass at 700 Hz — an extreme normalized-frequency ratio that scipy is well-documented to handle with catastrophic numerical imprecision. Confirmed by direct test: a clean sinusoid at *any* rate from 15 to 30 breaths/min all produced the exact same fabricated ~13 breaths/min output. This feature feeds directly into the WESAD LOSO classifier and the per-feature Cohen's-d table this project reports as methodology. | ✅ **Fixed** — switched to second-order-sections (`output='sos'`) form + `sosfiltfilt`, which recovers the true rate exactly in every case tested. Also proactively hardened the other two filters in the same file (`extract_hr_rmssd`'s bandpass, `extract_eda_features`'s two lowpasses) to `sos` as defense-in-depth, though direct testing confirmed those two were *not* numerically affected at their less-extreme ratios. **Real-world impact, re-measured**: WESAD LOSO accuracy moved from 91.86% to **91.53%** (F1 0.874→0.872) — a small, honest correction, not a headline-invalidating swing. `resp_rate`'s Cohen's d went from an unreported/likely-near-zero value to a real, physiologically plausible **+0.53** (baseline 16.7 bpm → stress 17.8 bpm — faster breathing under stress, exactly as expected). New regression tests (`test_wesad_calibration.py`) use a *tight* tolerance specifically chosen to have caught this bug, not the loose tolerance that let it slip past an earlier draft of the same test. |
| 2 | **Medium** | `wesad_calibration.py`'s `run_calibration()` completed the full ~30-minute pipeline and correctly wrote both output files, then **crashed** trying to `print()` its own summary to a plain Windows console — a literal Unicode `≥` (U+2265) character in the "HIGH ≥ {cutoff}" line can't be encoded in the default cp1252 codepage. Anyone running this script from a standard Windows terminal (not just this session's environment) would see a crash immediately after 30 minutes of real computation and might not realize the output files were actually saved correctly. | ✅ **Fixed** — replaced with ASCII `>=`, matching this project's own established plain-ASCII-output convention (already used elsewhere, e.g. `train_temporal_model.py`). Added a static regression test that parses the file's AST and asserts every string literal passed to `lines.append()` is pure ASCII, so this class of bug can't silently return in a *different* line next time. |
| 3 | Structural (no bug found) | `crop_face()` — the function that produces the exact pixels the CNN branch sees — is independently duplicated in **four** separate files (`app.py`, `stress_detector.py`, `benchmark_inference.py`, `evaluate_video_file.py`), each avoiding a Streamlit import in non-Streamlit entry points. None of the four copies had any test coverage before this audit; a drift introduced in any one copy's padding/clamping math would have gone completely undetected. | ✅ **Verified, not broken** — 17 new tests (`test_crop_face.py`) cover all four copies parametrically (no-face, full bounding box, edge-clamping, degenerate zero-width box) plus one direct cross-module test proving all four produce byte-for-byte identical output on the same input. No drift found; the duplication is now provably safe rather than merely assumed safe. |

## Modules re-verified by manual trace (no bugs found)

Given how much has been built since the last audit, these got a fresh adversarial read
rather than being trusted on the strength of their existing test suites alone:

- **`intervention_agent.py`** — full decision loop traced by hand: Thompson-Sampling scoring,
  Wilson-CI retirement, trend-based hold-back, multi-signal `'__general__'` competition, and
  every fallback branch (retired-specific-but-not-general, retired-both, empty-candidates).
  All edge cases resolve correctly; no bug found.
- **`temporal_model.py`** — the live NumPy GRU inference math and the 16-frame/8-frame
  sliding-window prediction schedule were checked step-by-step against the original design
  spec; both match exactly.
- **`retrain_from_sessions.py`** — confirmed the critical scaler-coordinate-space bug fixed in
  the 2026-08-23 audit is still correctly applied (`prior_scaler` reused consistently through
  `evaluate_lambda()`, `process_mode()`, and the final saved model) — no regression.
- **`analyze_rppg.py`** — checked for the *same* `(b,a)`-vs-`sos` numerical risk pattern that
  broke WESAD's filter, since both do scipy bandpass filtering. Confirmed **not** affected:
  realistic webcam frame rates (30–60 Hz) with a 0.7–3.0 Hz passband don't produce the extreme
  normalized-frequency ratio that caused the WESAD bug — verified by direct comparison of both
  filter forms, which agree exactly at this filter's actual operating parameters.
