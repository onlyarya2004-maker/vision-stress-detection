Browser-capture parity experiments (2026-09-27, UBFC-Phys s11, stride 2)
=========================================================================
Script: code/experiment_mediapipe_tasks_parity.py (--mode tasks | jpeg | resolution | pose-cadence)

Why these exist: the hosted app has to get camera frames from a user's BROWSER. Two designs were
evaluated against the validated Python pipeline (legacy mediapipe.solutions FaceMesh + Pose, the models
every reported number comes from):

(1) Detect landmarks IN THE BROWSER (MediaPipe Tasks API, WASM) and send only landmarks.  -> REJECTED
    Same BehavioralFeatureEngine, same footage, landmarks from the Tasks models vs the legacy models:
      detection agreement 5939 / 5974 frames; landmark position difference mean 4.77 px (median 3.80, p95 11.72)
      per-signal Pearson r: ear 0.967, ear_asymmetry 0.862, eye_strain 0.923, blink_stress 0.982,
          brow_tension 0.686, jaw_tension 0.182, head_instability 0.984, neck_strain 0.898, slouch 0.922
      BEHAVIOUR SCORE r = 0.486   (FAIL - brow + jaw carry 55% of the behaviour weight)
      relaxed-vs-stressed gap: legacy -0.055, Tasks -0.112 (the Tasks models would change the system's behaviour)
    A different model version is a different system: none of the validated accuracy numbers would transfer.

(2) Send compressed frames to the server and run the validated Python models there.        -> ADOPTED
    Question: does the JPEG hop alone change anything?  Legacy models on raw frames (A) vs on the same frames
    after a JPEG q80 encode/decode at 480 px (B):
      scored frames 5974, both detected 5953, legacy-only 0, B-only 0
      key-landmark position difference: mean 0.32 px (median 0.23, p95 0.83)
