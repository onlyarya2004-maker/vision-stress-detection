# What changed for the hosted demo (2026-10-10)

Nothing here is committed or pushed yet. Test suite: **529 -> 622 tests, all green.**
The validated model code (MediaPipe + CNNs + GRU + fusion maths, thresholds, weights) is
unchanged; no model was retrained and no dataset was added.

## New files
| File | What it is |
|---|---|
| `code/browser_camera/` | Streamlit component (plain HTML/JS). Shows the camera in the user's browser at full resolution, mirrors + 4:3-crops to 640x480, posts JPEG snapshots (~10/s, batched, acknowledgement-based backpressure), draws the label/face box the server sends back. `__init__.py` is its Python wrapper |
| `code/session_pipeline.py` | The ONE per-frame pipeline both capture modes call (`CalibrationRun`, `LiveRun`); `UserState` = one private engine/baselines/GRU/rPPG per login session; `BatchGate` = validation of everything a browser sends |
| `code/frame_ops.py` | Processing geometry (every model sees a centre-cropped 640x480), untrusted-JPEG decode, `crop_face`, `annotate_frame` (moved out of `app.py`) |
| `code/auth.py` | Supabase email/password login for the hosted app; refuses a service/secret key; optional invite code for sign-ups |
| `code/session_store.py` | `SupabaseStore`: same function names as `session_history.py`, per user, paged reads, explicit `user_id` filters |
| `supabase/schema.sql` | Tables + **Row Level Security** (the database itself enforces "you only see your own rows") |
| `Dockerfile`, `.dockerignore` | The hosted image (CPU TensorFlow, non-root, fails the build if the CNN weights are Git-LFS stubs; no datasets/recordings can enter it) |
| `deploy/DEPLOY.md` | Step-by-step runbook (image -> Supabase -> Azure -> auto-deploy -> demo-day checklist) |
| `deploy/github-workflow-*.yml` | Auto-deploy + Supabase keep-alive workflows (inactive until copied to `.github/workflows/`) |
| `scripts/rls_check.py` | Live proof against the real database that account B cannot read/change/delete/write account A's data |
| `scripts/load_test.py`, `scripts/platform_parity.py`, `scripts/serve_test_frames.py` | Capacity test, Windows-vs-Linux numeric check, fake camera for end-to-end tests |
| `models/browser_capture_parity.txt`, `models/pose_cadence_parity.txt` | The measurements behind the design (see below) |
| `.env.example` | The environment switches |

## Measured, not assumed
* **Why the server runs the models, not the browser** - `models/browser_capture_parity.txt`: browser-side MediaPipe
  gave behaviour-score r = 0.49 vs the validated pipeline (jaw 0.18, brow 0.69); JPEG compression alone r = 0.955 with identical mean.
* **Browser path = Python path** - a frame captured from the running browser component matches what the Python
  pipeline produces from the same source frame at 38 dB PSNR, and is clearly mirrored (9.9 dB if not).
* **Capacity** - `models/capacity_measurements.txt` (measured vs estimated, with the one open question):
  the models alone do 27 fps/user for 2 users on 2 CPUs, but the real live app is ~2.2x slower (cause unexplained);
  one live user alone on 2 CPUs gets 8.2 fps, so plan on **4 vCPU for the demo**. `POSE_EVERY_N_FRAMES = 3` is the spare
  lever (behaviour-score r = 0.999, `models/pose_cadence_parity.txt`).
